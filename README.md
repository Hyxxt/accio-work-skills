# Accio Work 自定义 Skill 实践：阿里国际站运营智能体

六个面向阿里国际站 B2B 业务的 Skill。基于 Anthropic Agent Skills 标准（Accio Work 与 Claude Code 通用），
在 Accio Work 上从零编写、迭代、用真实数据对照测试。

**仓库：https://github.com/Hyxxt/accio-work-skills**
安装包在 [`dist/`](dist/)，每个 Skill 一个 zip，可直接上传。

## 这是什么

调研阿里国际站「AI 运营 / 智能体方向」岗位时，JD 要求「在 Accio Work 平台独立设计、开发、上线 Skill」，
并明确列出六个业务场景。我先把这六个都写了一遍：

| Skill | 解决什么 | 核心方法 |
|---|---|---|
| [`inquiry-grading`](skills/inquiry-grading/SKILL.md) | 询盘分析与客户 ABCD 分级 | 硬信号 55 + 软信号 25 - 减分 20，四档映射 + 一票否决 |
| [`buyer-due-diligence`](skills/buyer-due-diligence/SKILL.md) | 客户背调与采购能力核验 | 域名核验 → 官网画像 → 领英交叉 → 风险标记，每条结论标来源 |
| [`store-health-diagnosis`](skills/store-health-diagnosis/SKILL.md) | 全店六维经营健康度诊断 | **按最低项定位短板**，不做加权平均（平台星级取最低能力项） |
| [`product-matrix-diagnosis`](skills/product-matrix-diagnosis/SKILL.md) | Top20 商品矩阵诊断 | 流量 × 转化四象限 + 同批相对基准，不用行业均值 |
| [`p4p-ad-diagnosis`](skills/p4p-ad-diagnosis/SKILL.md) | 直通车广告诊断 | `CPI = PPC / CVR` 拆因，关键词四象限止血 |
| [`brand-ad-diagnosis`](skills/brand-ad-diagnosis/SKILL.md) | 品牌广告（顶展/问鼎）诊断 | 曝光→点击→访客→询盘漏斗 + 三层归因分离 |

## 为什么这么做

先翻了平台技能库：搜索「客户」返回 16 个官方技能，覆盖竞品分析、客户声音、组织架构调研、RFM 分析等，
**但没有询盘分级这一类**。

这说明这几个场景属于企业自身的业务逻辑，平台不可能提供现成的——而这个岗位的核心职责，
就是把这些业务逻辑写成可执行的 Skill。所以判断一个候选人行不行，看的是「能不能从零写」，不是「装了多少」。

## 三条统一的设计原则

六个 Skill 的写法不同，但这三条是一致的。

### 一、判断靠规则，不靠模型感觉

所有分级、打分、阈值都固定在文档里。模型只做两件事：抽字段、按规则执行。

理由很直接：同一封询盘跑十次要得到同一个等级，同一份店铺数据跑十次要给出同一个诊断。
模型的感觉会漂，规则不会。

这和我在其他项目里的做法一致：**算钱的、判合格的环节交给代码，模型只负责听懂人话。**

### 二、缺输入就降级，不猜

每个 Skill 都有 `Input Handling`，按输入完整度分档：

- 字段缺失 → 正常执行，缺失项不加不减，并在结论里写明「追问什么可以升级」
- 只有摘要 → 照常判断，标注「未经原文核对」
- 完全没有 → 拒答，用固定模板列出所需字段

关键的一句写进了 `inquiry-grading`：**信息缺失是客户的问题，不是询盘质量的问题**。
不能因为资料不全就把整个判断压低——那是把「资料不全」错误地归因成了「客户不行」。

### 三、边界写死在文档里

每个 Skill 的 `Boundaries` 都明确禁止几件事：

- 不推测查不到的信息（写「未核实」而不是「看起来像」）
- 不承诺效果（不写「保证升 4 星」「保证降本 30%」）
- 不建议违规操作（刷单、刷点击、恶意点击）
- 不做超出范围的事（诊断类 Skill 不替客户定价、不做品牌策略）

实测证明这一条有效：`inquiry-grading` 跑出来的报告里自动加了两句我没字面写的话——
「官网实际有效性本轮未核实」「报价须经人工确认」。说明边界被理解并执行了，不是照抄条款。

## 两个值得单说的设计

### 全店诊断：为什么不做加权平均

阿里的商家星等级是**取各项能力星等中的最低值**。

这意味着六维平均 85 分、服务力只有 2 星，整店就是 2 星；把最强的一维从 4 星推到 5 星，对星级毫无帮助。
所以 `store-health-diagnosis` 的核心输出不是总分，而是：**最低项是谁、拉到下一档要做什么、差多少量。**

如果按常规做加权平均分，出来的建议会全部打偏。

### 品牌广告：为什么不能只看询盘成本

品牌广告买的是位置和曝光，用直通车的「询盘成本」直接判生死会得出错误结论。

所以 `brand-ad-diagnosis` 把归因拆成三层：直接归因（点进来产生的询盘）、间接归因（曝光后品牌词搜索提升）、
**不计入**（同期自然增长与季节性）。输出时必须分开写，并明确标注「第三层无法归因」。

诚实标注归因边界，比给一个好看的总数更有价值。

## 两轮迭代记录

好 Skill 不是写出来的，是跑出来改出来的。`inquiry-grading` 改了两版，两次都是**实际运行后发现的问题**。

### v1.1：补输入缺失的降级路径

**问题**：第一版只写了「不猜数量」，没写「连询盘内容都没有时怎么办」。
测一个官方 Skill 时发现，成熟做法是：缺什么就明说缺什么、列出所需字段、绝不推测。

**修改**：新增三档降级（字段缺失 / 只有摘要 / 完全为空）。

### v1.2：锁定输出语言

**问题**：英文询盘进去，整份报告变英文。但报告是给中国运营看的。

**修改**：新增 `Output Language`——报告主体中文、引用原文不翻译、仅回复要点用英文。
写死一句：**语言取决于读者是谁，不取决于输入是什么语言。**

## 测试结果

`inquiry-grading` 用两条对照用例，分别验证「打分路径」和「兜底路径」。

### 用例 A：完整询盘 → 走打分路径

输出 **A 级 70 分**，逐项列出依据，每项都能对回原文原句：

| 信号 | 得分 | 依据 |
|---|---|---|
| 明确数量 | +15 | Estimated quantity: 5,000 pcs |
| 明确规格 | +10 | 20W COB / IP65 / 5000mAh |
| 目标市场 | +8 | serving 120 retail stores across the southern US |
| 认证要求 | +7 | CE and RoHS certification |
| 目标价 | +5 | USD 12.50 per unit FOB Shenzhen |
| 采购周期 | +5 | lead time within 35 days |
| 公司可查 | +8 | 公司名 + 官网 + 企业邮箱（标注未核实有效性） |
| 专业提问 | +7 | 问 MOQ、包装、OEM 印刷 |
| 沟通完整 | +5 | 称呼、签名、职位、邮箱、电话齐全 |

未命中：平台认证买家、多轮历史（原文未提）

### 用例 B：垃圾询盘 → 走一票否决

`hello, please send me your catalog and best price list. we need many products. thanks`

输出 **D 级 0 分 hard D**，跳过打分直接否决，依据是只问目录不指产品、无数量、模板化、无联系方式。

### 一个观察

用例 B 走的是兜底通道，**完全没有触发打分逻辑**。
这说明测试要做两条：只测一条，会以为规则跑通了，其实只验证了兜底。

## 怎么安装

1. 从 [`dist/`](dist/) 下载对应 zip
2. Accio Work → 插件 → 技能 → 右上角「上传」
3. **两处都要开才生效**：Skills 页面 Enabled + 目标 Agent 的技能列表里 Selected
4. 对话中直接描述任务即自动触发，或输入 `/` 手动指定

## 与其他项目的关系

Skill 是对 Agent 能力的封装，和我的另外几个项目在做同一件事的不同层次：

- **理赔通**：Agent 自主调用条款检索与流程查询工具、最多六轮，工具调用过程可视化，免责场景明确拒赔
- **RAG 知识库**：检索与引用留在代码侧，模型只基于给定片段回答，资料不足时拒答
- **本项目**：把业务判断标准写成规则，让 Agent 稳定执行，缺输入时明确降级

三者共同的取舍：**把不确定的事留给模型，把要担责的事留给规则。**

## 说明

- 六个 Skill 的业务规则基于公开资料与行业通行做法整理，**具体门槛以平台后台当期口径为准**
- 示例数据均为虚构，不含任何真实客户与店铺数据
- 星级门槛每年调整，`store-health-diagnosis` 里引用的是 2025 版，使用时请核对后台
